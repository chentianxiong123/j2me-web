# 废弃尝试：长按连发（快速过剧情）

> 状态：**已放弃，代码已全部撤回**。本文只保留逆向发现和失败证据，供以后参考。
> 起止：2026-10-06，一天。
> 撤回点：本文件所在提交的前一个提交（JPEG 支持那一版）。

## 一句话结论

想法是「让模拟器在按住确认键时合成连发 `keyPressed`，这样只实现 `keyPressed`
的游戏（比如仙剑）就能按住连续翻页」。**实测用户侧无效，判定放弃。**

## 逆向发现（这部分结论可靠，有保留价值）

对 `仙剑奇侠传-忘情篇.jar` 做的字节码分析：

1. **游戏没有实现 `keyRepeated`。**
   MIDP 规范里「按住不放」走 `Canvas.keyRepeated(int)`；仙剑的画布基类
   `ag` 根本没这个方法，只在 `keyPressed` 里处理翻页。所以真机上也必须一下一下点。

2. **输入链路**：

   ```
   ag.keyPressed(code)
     → action = ag.b(code)              // 按键 → 内部动作
     → 场景对象 n.a(action, code)       // f.class（RolePlayingCanvas）
   ```

3. **`ag.b(int)` 完整映射表**（这个以后配 preset 会用到）：

   | 按键 | 内部 action | 含义 |
   |---|---|---|
   | keyCode 42 `*` | **32768** | **对话推进动作** |
   | keyCode 35 `#` | 65536 | — |
   | keyCode 48–57 `0-9` | 32 / 64 / 128 / 256 / 512 / 1024 / 2048 / 4096 / 8192 / 16384 | 菜单热键 |
   | 构造器传入的两个键码 | 131072 / 262144 | 左/右软键 |
   | 其余 | 走 `Canvas.getGameAction(code)` 再重映射：FIRE→1、UP→2、LEFT→4、DOWN→8、RIGHT→16 | 方向/中键 |

4. **`f.class` 里 `currentTimeMillis` 出现 0 次** → 没有任何节流/防连发守卫。

从 1、4 推出「合成的 `keyPressed` 会被游戏逐个处理」，所以这个思路在原理上成立。

## 失败证据（按发现顺序）

### 1. 我的实现有个真 bug：连发定时器从未启动

`InputManager.press()` 的结构是：

```ts
const existing = this.held.find((h) => h.source === source);
if (existing) {
  if (existing.timer === null) this.scheduleRepeat(existing);   // ← 后补的修复
  this.send('repeated', existing.sent);
  return;                          // ← 早退
}
...
this.scheduleRepeat(...);            // ← 原来排在这里，永远到不了
```

浏览器长按会持续发 keydown，第二次之后全部命中 `if (existing)` 早退分支，
而 `scheduleRepeat` 排在早退之后 —— **连发功能一次都没启动过**。

**为什么之前测出来「按住 1.2 秒有 11 次 pressed」**：那次测的是加探针之前的构建，
浏览器自动重复的 keydown 恰好落在 400ms 窗口内，制造了「连发在工作」的假象。
加上探针后（探针让派发路径本身变重，改变了时序）就测出「派发次数仍是 1」。
**教训：时序敏感的测试会自欺欺人，必须以「游戏侧真的执行了几次」为准。**

### 2. 只发按下不行，得补松开

第一版只合成 `pressed`。很多游戏自己维护「键是否已按下」标志，只补按下的话
标志一直是 true，后续按键全被当成「同一个键还按着」忽略。改成
`tap` 模式（按下 + 40ms 后松开）才符合真机点按的语义。

### 3. 探针测出：方法找到了，但一次都没真执行

在 `DisplayService.postKey` 里挂探针，记录派发到的 JVM 方法：

| 动作 | 派发次数 | 方法真实执行次数 |
|---|---|---|
| 单击空格 | 1 | **0** |
| 长按空格 1.2 秒 | 1（bug 修复前） | **0** |

探针记录到接收方法是 `ag.keyPressed(I)V`、`code = -5`（`KEY_FIRE`），
**键位映射是正确的**，但方法体一次都没跑起来。结合 `ag.keyPressed` 开头就有
`if (y) return` 这个屏蔽标志，判断是游戏侧把输入吞了，或事件循环时机不对。

**这一步没查到底就放弃了** —— 需要看到画面才能定位，光靠数字不够。

### 4. 用户实测无效（决定性）

实际游玩时按住空格没有任何效果，屏幕也不推进。

### 5. 诊断期间游戏崩过一次

```
Cannot read properties of undefined (reading '0')
  at ag.keyPressed (pc 0)
```

出现时机是「探针构建」上线期间。探针包装了 `m.code`（方法字节码），
**崩溃更可能来自探针本身而非长按功能**，但没能确认，也不想在废弃功能上继续投入。

## 为什么放弃而不是继续修

- 功能价值明确（省大量点按），但**我看不到画面，无法定位游戏侧为什么吞输入**，
  只能靠用户口述和屏幕哈希这类间接信号，而间接信号已经骗了我一次（见证据 1）。
- 已经出现了「自测结论与用户实测相反」的情况，再往下做需要能看见游戏画面的
  验证手段（截图 + 逐帧对比 + 文本 OCR），那是另一件事的成本。
- 投入产出不划算：模拟器还有更基础的缺口（如 `Form`/`List` 等 Screen 控件），
  那些是「一批游戏进不去」级别的问题，优先级高于「一个游戏少点几下」。

## 如果以后要重做，先做这三件事

1. **先有能看见的验证手段**：浏览器里把游戏 canvas 截图，配合文本层 OCR，
   确认「对话页序号」是否真的在推进，而不是看屏幕哈希变没变。
2. **先查清 `ag.y` 这个屏蔽标志**：在字节码里追谁在写 `y`，搞明白什么条件下
   `keyPressed` 会被整条丢掉。可能压根不该用「合成事件」这条路，
   而该直接让模拟器实现 `keyRepeated` 并在游戏侧补这个方法。
3. **先确认哪个键真正推进对话**：实测记录里 `*`（action 32768）才是引擎
   认的对话动作，而用户习惯按的是空格 —— 两者的映射关系要先用可见的方式确认。
