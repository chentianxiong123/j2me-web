# 静态托管方法论

> 适用范围：任何「所有计算都在浏览器里完成」的纯前端项目。
> 贯穿例子：本仓库的 j2me-web（含打包实验的产物形态）。
> 这是一份教程，也是本项目部署经验的整理。

---

## 0. 一句话结论

**静态托管的全部契约是：`GET /path` → 在磁盘上找到文件 → 原样返回字节。**

服务器不做任何计算。由此推出三件事：

1. 判断能不能静态托管，只问一句：**所有计算是否都在浏览器里完成了？**
2. 选型第一约束不是性能也不是价格，而是：**产物能不能进 git 历史。**
3. `curl` 返回 200 **只证明文件存在**，不证明它对。

---

## 1. 什么是静态托管

### 1.1 契约

```
客户端  GET /some/path
   ↓
服务端  在磁盘上找到对应文件
   ↓
       原样返回字节
```

服务端**不渲染、不查数据库、不执行你的代码**。这就是它便宜、快、不易坏的全部原因。

### 1.2 static-first 与伪静态

| 类型 | 特征 | 例子 |
|---|---|---|
| 彻底的 static | 没有任何服务端逻辑 | 本项目、文档站、纯前端 SPA |
| 伪静态 | 有服务端，只是多数路由返回文件 | SSR 的 Next.js、WordPress |

本项目属于第一类，不是「有个 Node 服务但不常用」那种。

### 1.3 什么项目**不该**上静态托管

- 需要服务端会话
- 需要按用户返回不同内容
- 需要定时任务
- 需要接收文件上传

这些场景请考虑 Serverless 函数或 VPS。真要混合，也应该先问一句：**这个需求能不能挪到客户端？**
（localStorage / IndexedDB 往往就够，本项目的存档就是这么解决的。）

## 2. 五条真正的约束

绝大部分「部署失败」都是下面 5 条之一，**与托管商是谁无关**。

### 2.1 路径必须相对

```html
绝对：  /assets/index.js        ← 放到子目录立刻 404
相对：  ./assets/index.js       ← / 和 /games/x/ 都能跑
```

Vite 里是 `base: './'`。这是**构建期**决定的，服务端救不了。

> 本项目踩过：`base` 曾是 `'/'`，放到 `github.io/j2me-web/` 下白屏。

### 2.2 HTTPS 与跨源隔离是两件事

新手常把这两个混为一谈：

| | 何时需要 | 触发条件 |
|---|---|---|
| HTTPS | 公网托管**平台**强制 | 与你的代码无关 |
| `Cross-Origin-Opener-Policy: same-origin`<br>`Cross-Origin-Embedder-Policy: require-corp` | **仅当**要用 `SharedArrayBuffer` | 跨源隔离能力 |

没用到 WASM 线程，则两者都不需要。

**推论（本项目实测成立）**：产物能跑在 `http://` 甚至 `file://` 上，
因为它不依赖任何要求安全上下文的 API。这让部署环境的选择面宽了一整档。

### 2.3 MIME 类型

| 扩展名 | 正确类型 |
|---|---|
| `.js` | `text/javascript` |
| `.css` | `text/css` |
| `.wasm` | `application/wasm` |

托管商默认都对。**自己拿 nginx 托管时**配错的症状很有迷惑性：
HTML 正常显示，但 JS 被拒绝执行。

### 2.4 缓存策略（决定用户体验，也决定怎么回滚）

```
index.html              →  no-cache                   ← 每次校验，否则用户卡在旧版本
assets/index-HASH.js    →  max-age=31536000, immutable ← 内容哈希变了才换名
```

文件名带 hash，是为了让「不可变资源」这个策略在安全上成立。
这也是每次构建后 JS 文件名会变（`index-DwTu34Xh.js`）的原因。

**回滚的前提**：新版本必须用新文件名。
如果产物文件名固定（`app.js`），那么 CDN 缓存会让回滚非常痛苦——
旧 JS 可能已经在边缘节点活了一小时。

### 2.5 单页应用的路由兜底

用了前端路由时，刷新深链 `/games/jianxin/detail` 会让服务端去找同名磁盘文件 → 404。

需要一条规则：**找不到文件时回落到 `index.html`**。

本项目不需要（单页面、无路由），但要知道这是**独立于**其他 4 条的坑。

## 3. 托管选项：按轴分类

选型不要问「哪个最快」，问两个问题：
**产物能不能进 git？要不要账号体系？**

| 方案 | 产物进 git | 需要账号 | 额度 | 适合 |
|---|---|---|---|---|
| **GitHub Pages** | **必须进** | GitHub | 1 GB 站 / 100 GB 月流量（软限制） | 纯代码、产物可公开 |
| **Cloudflare Pages** | 可选（direct upload） | Cloudflare | 流量基本不限 | 传大文件、产物不便入库 |
| **Netlify / Vercel** | 可选 | 各自 | 有免费层 | 需要分支 preview |
| **对象存储 + CDN**（S3/R2 + CloudFront） | 否 | 云厂商 | 按量，R2 无出网费 | 文件很大、已有云基建 |
| **自建 nginx** | 否 | 一台机器 | 自己的带宽 | 不想交出控制权、能自己搞 TLS |
| **IPFS / Arweave** | 否 | 无 | 按 pin 付费 | 内容寻址、抗审查 |

> 注意「免费额度」多为**软限制**：超了会告警或限速，不会立刻断。

## 4. 关键方法论：部署 ≠ 发布到 git

### 4.1 两种范式

```
范式 A：git-based（GitHub Pages 默认）

    git push ──> CI 构建 ──> 部署

    产物必须能被 CI 拿到
           ↓
      所以必须进仓库
           ↓
         进历史


范式 B：artifact-based（direct upload）

    本地构建 ──> dist/ ──> 上传到托管商

    产物永不进 git
```

### 4.2 选择规则（一句话）

> **产物如果不可公开（商业内容、授权限制、体积巨大不值得入库），
> 就必须用范式 B。**

### 4.3 为什么 git-based 不能拿来传不可公开的东西

两个不可逆的问题：

**（1）授权问题**
把完整商业游戏 jar 放进公开仓库，等于无授权分发。
谁都拿到链接就能下载。

**（2）技术上删不干净 —— 这是最反直觉的一点**

`git rm` 加 `force push` **救不回来**：

- 对象仍留在历史里，`git log` 照样能翻出来
- GitHub 的服务端缓存、第三方镜像、别人的 fork 都可能已经留着
- 「先推上去，试完再撤」这个想法在 git 上**不成立**

> git 里没有「删除」，只有「不再引用」。
>
> 删文件只是新提交里不再指向它；对象本身还在链上。

### 4.4 范式 B 的代价与典型命令

```bash
npm run build
npx wrangler pages deploy dist --project-name=my-site
```

或用托管商的 CLI / 网页拖拽上传。

**代价**：不好在 CI 里自动化，因为凭证（token）要管理。
所以范式 B 通常是「本地构建 + 手动上传」。

## 5. 验证方法论：200 不等于成功

本项目调试打包 bug 时完整走过这条路，值得单独记录。

### 5.1 反模式

```bash
curl -I https://example.com/     # 看到 200 OK 就宣布成功？
```

这只证明**文件存在**。

真实案例：打包 bug 的现象是「打开是空列表」，
而 `curl` 对 HTML 和 JS 全部返回 200——因为文件确实都在。
真正的错误是 `__PACK__` 赋值语句**排在 `boot()` 调用之后**，
属于纯逻辑错误，静态请求检查完全测不出来。

### 5.2 五层验证

| 层 | 手段 | 能证明什么 |
|---|---|---|
| **L1 文件层** | `curl -I` 逐个资源 | 服务器能返回字节 |
| **L2 内容层** | 下载后校验大小 / 魔数 / 哈希 | 返回的是**正确**内容，不是 404 页面 |
| **L3 引用层** | 解析 HTML/JS 里的相对路径，逐一 HEAD | 没有断链 |
| **L4 逻辑层** | 真实浏览器加载，看控制台与实际行为 | **代码真的按预期执行** |
| **L5 业务层** | 实际操作一次，看可观测结果落库 | 端到端通了 |

### 5.3 L4 必须真实浏览器

`curl` 和 jsdom 都给不了你「canvas 上画出了什么」。
带 UI 或游戏逻辑的项目，**L4 无法用其他方式替代**。

这是硬事实，早接受比晚接受省钱。

### 5.4 静态校验脚本的两个要点

```js
// 静态校验：不执行产物代码，纯解析
const bytes = Buffer.from(packed.game.jarBase64, 'base64');
assert(bytes.slice(0, 2).toString('hex') === '504b');   // ZIP 魔数
assert(origJar.equals(bytes));                           // 逐字节，不只是包含
```

1. **不要用「字符串包含」判断二进制完整性**
   base64 前缀会因转义、优化、chunk 边界产生误判。
   本项目就误判过一次，差点把问题定位到错误的方向。

2. **断言「字节相同」而不是「能解析」**
   逐字节比对是没有歧义的断言。

## 6. 决策流程（照着走）

```
1. 所有计算都在客户端吗？
      否 → 静态托管不适合，考虑 Serverless / VPS

2. 产物可以公开吗？
      否 → 必须用 artifact-based（direct upload），git-based 直接排除

3. 需要账号 / 认证 / 服务端状态吗？
      否 → 可零成本托管（Pages / Cloudflare Pages）
      是 → 先问能否改成客户端方案

4. 产物多大？
      < 5 MB 且需版本化 → git-based 可接受
      > 5 MB 或变化频繁 → artifact-based（仓库膨胀 + 构建成本都不划算）

5. 需要多分支 preview / PR 预览？
      是 → Pages / Netlify（这是它们相对 nginx 的核心优势）

6. 需要控制权 / 数据不出网？
      是 → 自建 nginx 或私有云

7. 怎么验证？
      按 L1→L5 逐层过，L4 必须真实浏览器
```

## 7. 本项目的具体结论

| 问题 | 答案 |
|---|---|
| 能静态托管吗 | 能，彻底的（无后端、无 WASM、无运行时外部请求） |
| 必须 HTTPS 吗 | **否**，`file://` 直接打开也能跑 |
| 必须子目录部署吗 | 否，`base: './'` 让它自由 |
| git-based 行不行 | 正式版（不含游戏）**可以**；含商业 jar 的产物**不行** |
| artifact-based 行不行 | 可以，需要托管商 token |
| 正式版体积 | 4 个文件 / 171 KB 未压缩 / 53 KB tar.gz |
| 打包版体积 | 3 个文件 / 1.72 MB / 1.20 MB tar.gz |
| 额度占比 | 1.2 MB ÷ 1 GB ≈ **0.12%** |
| L4 是否验证过 | **是**，用户在浏览器确认「打开即玩」 |

「无 WASM」这一点已核实：源码无 `WebAssembly` 引用、`package.json` 无 wasm 依赖、
正式产物 `WebAssembly`/`.wasm`/`instantiateStreaming` 命中数均为 0。
JVM 是纯 TypeScript 字节码解释器（`src/jvm/interpreter.ts`，`switch (op)` 派发）。

---

## 8. 三句话提炼

1. **先确认计算在哪一侧。**
   计算在客户端 → 静态托管是最优解；否则别硬上。

2. **产物能不能进 git，是选型的第一约束，不是性能也不是价格。**
   它决定范式 A 还是范式 B，而且 git 里没有删除。

3. **`200` 只证明文件在，不证明它对。**
   验证要分层，逻辑层只能靠真实浏览器。
